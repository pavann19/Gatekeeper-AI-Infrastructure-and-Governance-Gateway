# OWASP Compliance Mapping

Every row below cites a real control in this codebase, not an intention.
Where coverage is partial or a known gap exists, that is stated plainly —
see `docs/THREAT_MODEL.md` §8/§9 for the full accepted-limitations list and
`docs/ROADMAP_V2.md`'s Phase 8 section for the findings register these
controls were verified/hardened against, several of them via a live
black-box pentest against a real running instance
(`scripts/live_pentest.py`, `_evidence/live_pentest_results.json`).

This mapping covers two standards, since this project is both an HTTP API
and an LLM-facing gateway:
- **OWASP API Security Top 10 (2023)** — the generic API attack surface.
- **OWASP Top 10 for LLM Applications (2025)** — risks specific to being an
  AI governance gateway sitting in front of LLM traffic.

## OWASP API Security Top 10 (2023)

| # | Risk | Status | Real control |
|---|---|---|---|
| API1 | Broken Object Level Authorization | **Covered** | Every audit-log-reading endpoint (`/api/v1/activity`, `/api/v1/activity/trace/{id}`, `/api/v1/logs`) scopes results to the caller's own `tenant` server-side (`core.auth.resolve_principal`'s server-resolved `tenant`, never a client-asserted one) — `api/main.py`'s `_resolve_activity_tenant_scope`. Only `CAPABILITY_INTERNAL` may cross tenants via `?tenant=`. Verified live in Stage 1's pentest (`tenant_suspension` category) and by `tests/test_endpoint_auth_matrix.py` (81 tests). |
| API2 | Broken Authentication | **Covered** | `core/auth.py::resolve_principal` is the single trust boundary every endpoint uses — capability/tenant/key_id come from a server-side SHA-256 key-hash lookup (`hash_key`), never a client-asserted header. Raw keys are never logged or reconstructible (`tests/test_auth.py::test_principal_audit_record_contains_no_secrets`). 44 dedicated edge-case tests (`tests/test_auth_edge_cases.py`) including malformed-header sweeps, unicode/null-byte tokens, and a documented (non-exploitable) whitespace-handling asymmetry between the two auth entry points. |
| API3 | Broken Object Property Level Authorization | **Covered** | Every request schema in `api/schemas.py` uses `extra="forbid"` — an unrecognized field (e.g. a client trying to smuggle `role` or `capability` into a request body to self-escalate) is rejected outright, not silently ignored or trusted. `tests/test_schemas.py` and `tests/test_openapi_contract.py::test_extra_forbid_schemas_reject_unknown_fields_in_the_contract` confirm both the enforcement and that the OpenAPI contract documents it. |
| API4 | Unrestricted Resource Consumption | **Covered** | Per-tenant token-bucket rate limiting (`core/rate_limit.py`, `api/main.py::_enforce_rate_limit`) on every endpoint; daily token quotas for the LLM Gateway (`core/token_quota.py`); explicit size bounds on every request field that previously had none (`PolicyContentRequest.content` 1MB, `ToolCallRequest.arguments` 100KB serialized, tool/model/provider name fields 100–255 chars). **Distributed Rate Limiting & Quotas**: Implemented via Redis (`core/rate_limit.py::RedisRateLimiter` and `core/token_quota.py::RedisTokenQuotaTracker`). When `REDIS_URL` is configured, multi-worker deployments enforce exact shared quotas and rate limits across all replicas atomically via Redis Lua scripts with midnight/TTL expiry and graceful local in-memory fallback. **Found and fixed in review**: the MCP HTTP transport (`core/mcp_http_server.py`) originally reused the main API's `assess_rate_limiter` singleton for its own rate limiting, so a caller's MCP and main-API traffic would drain one shared budget once Redis-backed — fixed with a dedicated `mcp_rate_limiter` singleton and its own key namespace (`docs/THREAT_MODEL.md` §7 finding #13). |
| API5 | Broken Function Level Authorization | **Covered** | Every INTERNAL-only endpoint (policy admin, review resolution, raw logs, tool/gateway catalogues, cache flush) checks `principal.capability != CAPABILITY_INTERNAL` before doing anything — confirmed exhaustively in Stage 1's pentest and `tests/test_endpoint_auth_matrix.py`, including the specific (intentional) behavior that a missing credential on an INTERNAL-only endpoint returns 403, not 401, since the capability check runs before any auth-requiredness check. |
| API6 | Unrestricted Access to Sensitive Business Flows | **Partial** | The Human Review flow (`core/review_queue.py`) exists specifically to gate MEDIUM/ambiguous-risk flows behind human approval rather than full automation, and HIGH-risk tool calls (e.g. `demo.database.delete`) always require review "even for an INTERNAL caller" (`core/demo_tools.py`). No CAPTCHA/anti-automation layer exists for the assess/gateway endpoints themselves — rate limiting is the only friction against scripted abuse, which is an accepted tradeoff for a machine-to-machine API (a human-facing CAPTCHA would break every real integration). |
| API7 | Server Side Request Forgery | **Covered, verified live** | `core/real_tools.py`'s `http.get` tool enforces an exact-match hostname allowlist (`TOOL_HTTP_GET_ALLOWED_DOMAINS`, empty/fail-closed by default) plus a call-time DNS-resolution check (`_resolved_addresses_are_all_public`) rejecting private/loopback/link-local/reserved/multicast resolved addresses — defeats DNS-rebinding, not just a hostname-string check. **Found and fixed during this hardening effort**: the tool was fully built and tested but never actually wired into any real startup path (`REGISTER_REAL_TOOLS`, see `docs/ROADMAP_V2.md`) — a real deployment had zero SSRF exposure only because the vulnerable-if-misused code was unreachable, not because the protection was exercised. Re-verified live post-fix: all 5 SSRF probe targets (cloud metadata IP, loopback variants, IPv6 loopback, `0.0.0.0`) correctly rejected; a real allowlisted domain succeeds. |
| API8 | Security Misconfiguration | **Covered** | CORS defaults to no credentialed cross-origin access without an explicit allowlist (`api/main.py`, logged warning on wildcard); the Docker image runs as a dedicated non-root user (Phase 8, verified against real builds/volumes, catching a real `/app/audit` mount-ownership bug in the process); Prometheus metrics require auth when `METRICS_REQUIRE_AUTH` is set and are excluded from the public OpenAPI schema; every "should this be on by default" flag in this codebase (`REGISTER_DEMO_TOOLS`, `REGISTER_REAL_TOOLS`, `DOMAIN_GUARDRAIL_MODE`, `HALLUCINATION_CHECK_ENABLED`) defaults to the conservative/off setting, requiring explicit opt-in. |
| API9 | Improper Inventory Management | **Covered** | The generated OpenAPI schema (`tests/test_openapi_contract.py`) is validated spec-conformant and checked to actually document every real route; the Developer UI's Tool/Model Gateway pages (`/ui/gateways/`) show the REAL registered tool/provider catalogue read live from the same registry the enforcement code uses, not a hand-maintained description that can drift. |
| API10 | Unsafe Consumption of APIs | **Covered** | The LLM Gateway's provider fallback chain (`core/llm_providers.py`) wraps every outbound provider call in `LLMProviderError` handling with explicit timeout/connection-error paths, never silently trusting a malformed upstream response; usage/token extraction is defensive per-provider (`extract_total_tokens`), tested for missing/malformed `usage` fields (`tests/test_llm_providers_edge_cases.py`). |

## OWASP Top 10 for LLM Applications (2025)

| # | Risk | Status | Real control |
|---|---|---|---|
| LLM01 | Prompt Injection | **Covered, verified live** | Multi-layer detection: symbolic hard-ban regex (`core/risk.py::hard_ban_triggered`), a 9-feature fusion ensemble of specialized detectors (`core/fusion.py`), semantic similarity against known threat anchors, and LLM-judge arbitration (Llama Guard 3 / Ollama) for ambiguous cases. Stage 1's live pentest ran a 10-prompt real jailbreak corpus (DAN-style, system-override framing, base64-obfuscated, "hypothetical thought experiment" framing) against the real running pipeline — all correctly BLOCK/REVIEW/RESTRICT, zero false negatives, with a paired benign-prompt control confirming no blanket over-blocking. |
| LLM02 | Sensitive Information Disclosure | **Covered, one real gap found and fixed** | Input PII redaction (`core/privacy.py`: AADHAAR, EMAIL, IP, PHONE regex + NER for GPE/ORG/PERSON, with per-tenant disabled patterns and custom NER labels) runs before caching, judge calls, or logging. Output-side: secrets detection (hard BLOCK, no redact-and-continue — a credential has no safe partial form) and PII redact-and-continue (`core/output_guardrails.py`). **Found live**: the PII redaction's `[REDACTED:PERSON]`-style placeholder token was itself anomalous enough to trigger false-positive blocking in the fusion detectors — fixed by routing only the local, non-persisted classifiers onto the original text (`assess_risk`'s new `raw_prompt` parameter) while keeping the embedding, persisted cache, and judge escalation on redacted text exactly as before. |
| LLM03 | Supply Chain | **Partial** | Dependencies are version-pinned with explicit lower bounds (`requirements*.txt`) and API keys are the only "credential-shaped" secret this project manages directly (SHA-256 hashed at rest, `core/auth.py`). Automated dependency-vulnerability scanning is now wired into CI via `.github/workflows/dependency-audit.yml`, which runs `pip-audit` against all three Python requirements manifests on push/PR to `main` and weekly. Model-provenance verification is still not automated. |
| LLM04 | Data and Model Poisoning | **Not directly applicable** | This project does not train or fine-tune models; it orchestrates pre-trained third-party models (sentence-transformers, Llama Guard, Ollama-served LLMs) and its own small hand-curated anchor/policy corpora (`policies/*.json`). Those corpora are code-reviewed, version-controlled JSON, not user-submitted training data — no live poisoning surface exists in the sense this risk category describes. |
| LLM05 | Improper Output Handling | **Covered, two real gaps found and fixed** | `core/output_guardrails.py::assess_output` runs secrets → system-prompt-leak → PII-redact → toxicity-judge → (optional) hallucination-grounding, in that order, before a response is ever returned. **Found live (gap 1)**: the hallucination/grounding check compared output text against `educational_store`'s centroid — actually the INPUT-side educational-context anchor set, a category error that could BLOCK any legitimate response once that store warmed up from prior traffic. Fixed by gating it off by default (`HALLUCINATION_CHECK_ENABLED=False`) rather than deleting the check, pending a real output-domain reference corpus. **Found (gap 2)**: `output_judge()` returning its `JUDGE_OFFLINE` sentinel when the primary judge (Ollama/Llama Guard) was unreachable fell through `assess_output`'s `if verdict == "DANGEROUS"` check to silent ALLOW — a fail-open exposure whenever the judge backend is down. Fixed with a local fallback judge (`core.semantic_judge._fallback_output_judge`, reusing the already-warmed `toxic_bert` detector, `OUTPUT_JUDGE_FALLBACK_ENABLED` default on) that engages before the bare offline sentinel is ever returned; true fail-open now requires BOTH the primary judge and this fallback to be down. Verified live (71ms warm-call latency, correct real classification) — see `docs/THREAT_MODEL.md` §7 finding #16. |
| LLM06 | Excessive Agency | **Covered** | The Tool/Agent Gateway (`core/tools.py`, `core/real_tools.py`, `core/mcp_server.py`, `core/mcp_http_server.py`) enforces per-tool `capability_required` and `risk_level`, with HIGH-risk actions always routed to human review (`core/review_queue.py`) regardless of caller capability — "always requires human review, even for an INTERNAL caller" is enforced in code, not just documented. Every tool argument is JSON-Schema validated (including `maxLength`) before execution. The only real (non-sandboxed, network-calling) tool, `http.get`, is opt-in at deployment (`REGISTER_REAL_TOOLS`, off by default) and hostname-allowlisted. |
| LLM07 | System Prompt Leakage | **Covered, verified live** | `core/output_guardrails.py::check_system_prompt_leakage` does a sliding-window verbatim-substring check (not just semantic similarity, which would conflate "about the same topic" with "contains the actual text") against a caller-supplied reference prompt, hard-BLOCKing on a match ≥40 contiguous characters. Verified live in Stage 1's pentest with a real system-prompt-leak probe. |
| LLM08 | Vector and Embedding Weaknesses | **Partial** | The semantic cache (`core/cache.py`) and threat/educational vector stores (`core/vector_store.py`, real FAISS indexes) are process-local and never persist raw prompt text, only hashes/embeddings — an embedding-inversion attack against the persisted cache is a real, generic risk class for any embedding-based system and is not specifically hardened against here beyond not storing the raw text alongside the vector. No cross-tenant embedding leakage: cache/vector-store lookups are not tenant-partitioned today, meaning a fuzzy-match hit from one tenant's traffic could influence another's cached risk verdict for a similar prompt — this is an accepted architectural simplification (the risk VERDICT can leak by similarity, never the underlying text), not yet a stated limitation in `docs/THREAT_MODEL.md`; worth adding there. |
| LLM09 | Misinformation | **Out of scope by design** | This project is a governance/security gateway sitting in front of LLM traffic, not the LLM generating content — it detects known risk patterns (attacks, PII, secrets, toxicity) in text, not factual accuracy of LLM-generated claims. The disabled-by-default hallucination check (LLM05 above) was an attempt at a narrow slice of this and was found miscalibrated; a real solution would need a domain-specific factuality corpus, explicitly out of this project's current scope. |
| LLM10 | Unbounded Consumption | **Covered** | Per-request timeouts on every assessment path (`ASSESS_TIMEOUT_SECONDS`, `GATEWAY_TIMEOUT_SECONDS`) that fail closed with a 503 rather than fabricating a verdict; bounded thread pools (`_assess_pool`, `_gateway_pool`) so a stuck call costs one worker, not the whole process; per-tenant rate limits and daily token quotas (distributed across instances via Redis); a real load test (Stage 4, this document) established measured p50/p95/p99 latency SLOs under realistic concurrency — see the Performance section below. |

## Performance SLO benchmark

Real load test (`scripts/load_test.py`) against a real running instance — real concurrent HTTP connections, not estimated or simulated figures. Raw data: `_evidence/perf_slo_benchmark.json`.

| Endpoint | Concurrency | Requests | Throughput | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| `GET /health` (zero-I/O baseline) | 20 | 300 | 301.1 rps | 64.4ms | 69.4ms | 88.4ms |
| `GET /api/v1/whoami` (auth + tenant resolve) | 20 | 300 | 642.4 rps | 28.8ms | 36.9ms | 39.2ms |
| `GET /api/v1/activity` (audit-log tail read) | 20 | 300 | 228.0 rps | 85.3ms | 95.5ms | 99.5ms |
| `POST /api/v1/assess` (full detection pipeline) | 10 | 100 | 6.9 rps | 558.8ms | 9245.6ms | 9622.4ms |

All requests returned their correct expected status code (200, or 429 once the tenant's real rate limit was legitimately exceeded — see below) — zero 5xx errors, zero connection failures, across all four runs.

**`/api/v1/assess`'s p50/p95 gap is real and explained, not noise**: 100 concurrent requests for the *same* prompt were used to also exercise the semantic cache under load. p50 (559ms) reflects requests that landed on a warm cache entry; p95/p99 (9.2–9.6s) reflect the requests that raced the very first, uncached call through the full pipeline (fusion detectors + LLM judge arbitration via Ollama) before the cache was populated. This is the real, worst-case cold-path latency for a genuinely novel prompt, and it is why `ASSESS_TIMEOUT_SECONDS` defaults to 30s and every assessment path fails closed with a 503 (never a fabricated verdict) past that deadline — see `core/risk.py::assess_risk`'s docstring and `api/main.py`'s timeout handling.

**A real, serious bug was found and fixed by this exact benchmark**: the first `whoami` run under concurrency showed 12/300 (4%) spurious `401 Unauthorized` responses for a demonstrably valid API key. Root cause: `core/auth.py::KeyStore.load()` set `self._loaded = True` *before* finishing repopulating `self._keys`, so a concurrent `lookup()` from another thread (real concurrency — FastAPI dispatches sync endpoints like `whoami` to a thread pool) could observe an empty or half-built dict during the window right after a fresh load or a forced reload. Fixed by building the new key dict in a local variable and only swapping it into `self._keys` in one atomic assignment after it's fully populated, with a lock serializing concurrent loads (`tests/test_keystore_concurrency.py`). Re-running the identical load test after the fix: **0/300 spurious 401s**, confirmed live, not just in unit tests.

**Distributed Rate Limiting & Token Quotas Deployment Note**: Single-process testing validates in-memory baseline operations. In horizontally-scaled multi-worker deployments, configuring `REDIS_URL` shares rate-limiting token buckets and daily token quotas across all gateway worker processes.
